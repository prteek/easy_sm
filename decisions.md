# Principles

- **Don't break existing projects** (2026-10-13) — template scripts are copied into user projects by `init` and `executor.sh` is baked into the image at build, so a fix only reaches users after `easy_sm update-scripts` (+ rebuild/push). New behaviour therefore checks for outdated copies and stops with instructions (`process_local.sh` `--env`, `require_run_support`) instead of changing behaviour silently. Same reason `~/.aws` stayed writable and existing local commands keep exit code 0.
- **Unix-style CLI** (`b66fef7`) — cloud commands at the top level (no `cloud` prefix), app name auto-detected from the single `*.json`, IAM role from `SAGEMAKER_ROLE`, and output is only the data (S3 path, job or endpoint name) so commands pipe into each other.

# CLI design

- **Typer, not Click** (`e5ade8c`) — options declared with `Annotated` type hints; Click groups became Typer sub-apps.
- **No `cloud_app`** — it was never registered; cloud commands are plain functions registered in `__main__.py`, where names and `context_settings` belong. `--help` for all 14 commands identical before and after removal.
- **Image tag from config, not a CLI flag** (`2f97df7`) — `docker_tag` lives in `{app_name}.json` so each app/model version can use its own tag; the global `--docker-tag` option was removed (user docs still mention it: open).
- **Wait by default, `--no-wait` to opt out** (`0eba322`) — `train` and `process` (and `run`) wait for the job; reverses the fire-and-forget behaviour from the v3 simplification (`81e2c05`), which returned an S3 path before the job had finished.
- **Deploys always wait and verify the new config; no `--no-wait`** (2026-10-15) — `deploy` / `deploy-serverless` (create or update) wait for `endpoint_in_service`, then fail (exit 1) unless the endpoint is `InService` on the **new** config. A failed update also ends `InService` after rolling back, so the config name is the real check. Before, the command returned as soon as the update started and CI smoke-tested the old model. No `--no-wait`, unlike `train`/`process`: a deploy that returns before it is known to work is the bug.
- **Kept create-or-update, no separate `update-endpoint`** (2026-10-15) — callers run one command whether or not the endpoint exists, and splitting wouldn't change the wait/verify logic. A rollback command (point an endpoint at an existing config) is a different operation, possible later.
- **easy_sm never deletes resources on its own; cleanup is the user's job** (2026-10-15) — updates used to delete the previous endpoint config right after `update_endpoint`. SageMaker allows that mid-rollout, so when the new model crashed it rolled back to a deleted config and the endpoint could no longer be updated (incident 2026-10-15; CloudTrail shows the delete one second after the update). Config names are unique per deploy (`hash()` per run, `62c900e`), so keeping them never collides; the cost is that configs and models accumulate until the user deletes them (`delete-endpoint --delete-config` or the AWS CLI). Deploying to an endpoint whose current config is already missing stops with a clear error instead of SageMaker's `ValidationException`.
- **Short flags don't collide within a command** (`e25c95d`) — `-c` is always instance count; serverless max concurrency became `-mc`.
- **`requirements_dir` kept** — renaming it to `requirements_file_name` was tried and reverted the same day (`9d7365e` → `472c0a1`) because requirements can live in different folders for different scenarios (e.g. dev vs prod), so the config points at a location, not a fixed file name.

# CLI redesign (2.0, hf-style, 2026-11-03)

Goal: move towards the `hf` CLI's UX: commands grouped by resource and then action, the main object as a positional argument, defaults instead of required flags, one output convention, and as little user-side boilerplate as possible. **A complete rewrite with no backward compatibility** (chosen 2026-11-03): no aliases for old commands or flags, no migration from `{app}.json`, no fallbacks for old project layouts or already-built images. This supersedes *Principles: Don't break existing projects* for 2.0. Nothing is implemented yet; items not marked chosen are proposals.

- **CLI command stays `easy_sm`** (chosen 2026-11-03) — shorter names were tried and dropped for simplicity: `es` (clashes with a Unix shell and voidtools Everything's Windows CLI) and then `esm`. One name everywhere: the PyPI package, the command, the module and `easy_sm.toml`, so there's nothing to map between.
- **Command tree** (proposed) — `init`, `env` (resolved app, profile, region, role, image, like `hf env`), `build`, `push`, `train [--local]`, `run [--local] cmd...`, `jobs ls|inspect|logs|cancel|artifacts`, `endpoints ls|deploy|describe|invoke|delete|serve --local`, `data upload`. Output is a table by default, with `--format json` and `-q` (IDs only) for pipes.
- **`--local` flag, not a `local` sub-app** (chosen 2026-11-03) — `easy_sm train --local` → `easy_sm train` states the product's point (prototype locally, then run the same command in the cloud) and halves command code and docs. Cloud-only flags are rejected with `--local`.
- **One flag vocabulary** (proposed) — today `-r` is the IAM role in `cloud.py` but the region in `push.py`; `-e` is EC2 type, instance type or external ID; `-n` is job prefix, endpoint name or names-only. There are synonyms (`--ec2-type`/`--instance-type`, `--instance-count`/`--num-instances`, `--input-s3-dir`/`--s3-input-location`) and two-letter short flags (`-mc`, `-is`) (checked in `cloud.py`, `push.py`). New set: `--instance`, `--count`, `--env`, `--env-file`, `--timeout` (e.g. `2h`, replacing the hard-coded 24 h `MaxRuntimeInSeconds`), `--no-wait`, `--local`, `-q`, `--format`, `-n` (how many, for `ls`). Names follow `hf jobs run` where SageMaker has an equivalent (`--flavor` → `--instance`).
- **`easy_sm.toml`, one app per folder** (chosen 2026-11-03) — TOML allows comments and per-command sections, and is read with stdlib `tomllib`. Only `init` writes it, from a template string, so no `tomli-w`. The fixed name removes `-a`, `auto_detect_app_name` (whose `glob("*.json")` breaks on any other JSON file in the folder) and app-name path validation; `app_name` becomes a field. Like `pyproject.toml`, one per folder. Stays separate from `[tool.easy_sm]` in `pyproject.toml`: AWS roles and instance types aren't package metadata.
- **Global `--config` option** (proposed) — `easy_sm --config prod.toml train`, defined once on the app callback. It's an escape hatch, so being less discoverable is fine.
- **Job and endpoint settings live in the config file; flags override per run** (chosen 2026-11-03) — `[aws]` profile/region/role, `[train]` instance/count/input/output, `[run]` instance/timeout and default `env`, `[endpoint]` name/instance/serverless/memory/concurrency; the job prefix defaults to `app_name`. Values resolve as flag → env var (`AWS_PROFILE`, `AWS_REGION`, `SAGEMAKER_ROLE`) → `easy_sm.toml` → built-in default. The file documents how the project runs and deploys; a run that needs something else overrides it (`easy_sm run --instance ml.m5.4xlarge python features.py`). Considered and dropped the same day: hf-style runtime flags only, with config reduced to app name and AWS context. The project file was preferred as the place to record endpoint and job settings. `easy_sm train` needs no flags.
- **No `process` command; use `run python script.py`** (chosen 2026-11-03) — `executor.sh`'s `process` branch is `cd processing; python "$2"` and `run` is `cd processing; exec "$@"`, both through `_run_processing`, so `process` was a special case of `run`. `run` lets the script take arguments and propagates the exit code (`local process` exits 0 on failure). Keep a pre-flight check that a `python x.py` target exists, so a typo doesn't start a cloud instance. `train` stays separate: a different SageMaker job type (model artifacts, input channels) that endpoints depend on.
- **No shell scripts in projects; docker driven from Python** (proposed) — `local_test/*.sh`, `build.sh` and `push.sh` are copied into each project and run from there, which is the only reason `update-scripts`, the outdated-script guards (`require_run_support`, the `IFS=','` check) and most of the shell-quoting work exist. Building argv lists in Python (subprocess list or the `docker` SDK, already a dependency) removes all of them; `test_local_scripts.py` becomes tests of the generated docker argv.
- **Push via boto3 + docker SDK, not `push.sh`** (proposed) — `push.sh` needs the `aws` CLI, runs `aws configure set` and so **writes to the user's `~/.aws/config`** whenever a role is passed, and has an `eval` aws-cli v1 branch. `sts`, `ecr.describe_repositories`/`create_repository` and `get_authorization_token` replace it; `push`'s `--external-id`/`--aws-profile` flags go.
- **Build and push implicitly, tagged by content hash** (chosen 2026-11-03) — `hf` never asks the user to build: `hf jobs run IMAGE` runs an existing image, `hf jobs uv run` installs dependencies at runtime, Spaces build remotely. easy_sm equivalent: job commands hash source + `uv.lock` + Dockerfile + runtime and build/push only if ECR lacks that tag (`--local` builds only; `--no-build` opts out). Jobs can't silently run stale `:latest` code, and each job is pinned to an immutable image, so `docker_tag` goes. `build`/`push` stay for CI and Dockerfile debugging.
- **uv for dependencies at build time, not at run time** (chosen 2026-11-03) — projects have `pyproject.toml` + `uv.lock`; the Dockerfile runs `uv sync --frozen --no-dev` (uv copied from a pinned `ghcr.io/astral-sh/uv` image), lockfile copied before source so code edits don't reinstall dependencies. Removes `requirements_dir` (its dev/prod reason is covered by uv dependency groups) and `python_version` (from `requires-python`/`.python-version`). Fixes the template's unpinned `pip install flask`. No `requirements.txt` support.
- **Rejected or deferred image options** (2026-11-03) — `--image` for arbitrary images: deferred, since SageMaker training and processing pull only from ECR. Remote builds (CodeBuild, Spaces-style): deferred; they would avoid QEMU amd64 emulation on Apple Silicon (`build.sh` forces `--platform linux/amd64`) but need a CodeBuild project, a role and S3 staging. No-image `uv run` style: rejected, because the image is what guarantees local == cloud; runtime installs are also slow and need internet access inside the VPC.
- **User code is two functions; easy_sm ships the runtime** (chosen 2026-11-03) — borrowed from HF Inference Endpoints' `handler.py` (`EndpointHandler.__init__(path)` / `__call__(data)`), where the platform owns the server. Users write `train(input_dir, model_dir)` in `src/train.py` and a `Handler(model_dir)` with `__call__(data)` in `src/predict.py`. Today the template's `prediction/serve` is a 57-line Flask app run on Flask's development server (`app.run`) in production, CSV-only with pandas, and `training/train` is 60+ lines of argparse around a 7-line `training.py`; all of it is copied into projects and never updated. New: an `easy_sm/runtime/` module copied into the build context by `easy_sm build` (one PyPI package, runtime always matches the CLI that built the image), entrypoint `python -m runtime train|serve|run` replacing `executor.sh`, `training/train` and `prediction/serve`. It serves with gunicorn (`/ping`, `/invocations`, one worker per CPU, SageMaker timeouts), decodes JSON by default and CSV via stdlib `csv` (optional `decode`/`encode` hooks on the handler), and writes training exceptions to `/opt/ml/output/failure` so they show as the job's `FailureReason`. A custom `Dockerfile` with its own `ENTRYPOINT` is the escape hatch (e.g. FastAPI).
- **Runtime details** (chosen 2026-11-04, step 2) — `easy_sm/runtime/` is standard-library only (a test parses its imports) and uses relative imports, so it works copied into the image as top-level `runtime`. Responses are always JSON; CSV requests reach the handler as rows of strings (no type guessing); a result that isn't JSON-serialisable is a 500 with the reason in the logs. The training failure file starts with a one-line `Type: message` summary because SageMaker's `FailureReason` shows only the first 1024 characters. `run` replaces itself with the command (`os.execvp`) so the command's exit code is the job's, and `.py` files run with `sys.executable` (the image's Python). Functions take their folders as arguments; only `runtime/__main__.py` uses the real `/opt/ml` paths.
- **Deploy from a training job, not an S3 path** (chosen 2026-11-03) — `easy_sm endpoints deploy churn-ep <job>` (or `--latest`), like HF deploying from a repo ID. The job record holds both the model artifact and, with content-hash tags, the exact image it was trained with. Today `deploy` takes the image from the config (`cloud.py:25`), so rebuilding after training silently serves the old model with new serving code. An S3 path is still accepted, for models trained outside easy_sm. Replaces the `$(easy_sm jobs artifacts $(easy_sm jobs ls -q -n 1))` pipe.
- **One `invoke` for local and cloud; `serve --local` runs in the foreground** (proposed) — `easy_sm endpoints invoke --local -d @x.json` / `easy_sm endpoints invoke churn-ep -d @x.json`, like HF's `InferenceClient`, so one smoke test works before and after deploy and in CI. Ctrl-C stops a local server, so there's no stop command.
- **`run` takes the command directly, like `hf jobs run IMAGE python ...`** (proposed) — no `--` in docs or examples: `easy_sm run --local python clean.py --date 2026-11-01`. Already works today, because option parsing stops at the first word of the command (see *Run command: Option parsing stops at the command*); `--` is only needed when the command itself starts with `-`. Optional shorthand, like `hf jobs uv run script.py`: a first argument ending in `.py` runs with `python`, so `easy_sm run clean.py --date 2026-11-01`; that is also where the pre-flight existence check lives.
- **Stream job logs while waiting** (chosen 2026-11-03) — today cloud `train` calls `create_training_job` with boto3 and then waits on `training_job_completed_or_stopped` with no output until the job ends (`sagemaker.py` `train`), while processing jobs stream logs through the SDK's `Processor.run`. New: `train` and `run` follow the job's CloudWatch logs (`/aws/sagemaker/TrainingJobs` or `/aws/sagemaker/ProcessingJobs`, streams prefixed with the job name) until it finishes. There's one log follower shared with `jobs logs -f`, written on boto3 `logs` rather than the SDK's `logs_for_job`, which prints to stdout. Logs and status lines go to **stderr**, so stdout still carries only the job name and `$(easy_sm train)` keeps working; the same applies to local container output. Multi-instance jobs prefix each line with the host (`[algo-1]`). Ctrl-C stops following but leaves the job running, and prints the `jobs logs -f` / `jobs cancel` commands. Exit code is non-zero on failure, printing `FailureReason`. `-q` waits without logs; `--no-wait` prints the job name and returns.
- **No scheduling** (rejected 2026-11-03) — considered `--schedule` like `hf jobs scheduled`, via EventBridge Scheduler calling `CreateProcessingJob`/`CreateTrainingJob` directly. Dropped as needless complexity: it needs a second IAM role for Scheduler (`iam:PassRole`), unique job names per run via `<aws.scheduler.execution-id>` (unverified), a `schedules` command group, and failure alerts for runs nobody watches. Event triggers (S3 uploads) and chaining (train → deploy) would need a Lambda or Pipelines on top. Use an external scheduler instead, e.g. a CI cron job running `easy_sm train && easy_sm endpoints deploy ep --latest`; pipe-friendly output makes that enough.
- **Sample workflow** —
  ```bash
  easy_sm init && easy_sm env
  easy_sm train --local
  easy_sm run --local python clean.py --date 2026-11-01
  easy_sm endpoints serve --local                  # Ctrl-C to stop
  easy_sm endpoints invoke --local -d @sample.json
  easy_sm data upload ./data s3://bucket/churn/data
  easy_sm train                                    # builds + pushes if the hash changed; prints the job name
  easy_sm run --instance ml.m5.4xlarge --env LOG_LEVEL=debug dbt build -t prod
  easy_sm jobs ls; easy_sm jobs logs <job> -f; easy_sm jobs cancel <job>
  easy_sm endpoints deploy churn-ep --latest
  easy_sm endpoints invoke churn-ep -d @sample.json
  easy_sm endpoints ls; easy_sm endpoints delete churn-ep --delete-config
  easy_sm jobs ls --format json | jq '.[0].status'
  ```
- **Delete all tests and docs; restart minimal** (chosen 2026-11-03) — the 167 tests and the MkDocs site describe the 1.x CLI, which the rewrite replaces entirely. Start with a few plain pytest tests, written to understand the code, and **no mocks of SageMaker, boto3 or Docker** at first. To make that work, keep AWS and Docker calls thin: pure functions build the request (the `CreateTrainingJob` dict, the `docker run` argv, the image hash, the config lookup) and are tested directly; the call that sends it is one line and is checked by running the workflow against a real account. Docs restart as one README with the sample workflow. Goes with them: `docs/`, `mkdocs.yml`, `requirements-docs.txt`, `docs.yml`, `scripts/validate_docs.py`, `.githooks/pre-commit`, `DOCS_WORKFLOW.md`, the `validate-docs` skill and `tests/LOCAL_COMMANDS_TESTS_README.md`; `test.yml` keeps pytest, mypy and ruff. Kept: `summary.md`, `decisions.md`, `todolist.txt`. CLAUDE.md is rewritten to match. Supersedes *Testing and docs* below for 2.0.
- **Runtime dependencies are only `typer` and `boto3`** (chosen 2026-11-03) — the SageMaker SDK (pinned `==2.257.3`) goes: `train` already used plain boto3, and processing jobs, endpoints, the default bucket and logs need only boto3 calls; it also removes the import-time logging workaround. The `docker` Python SDK goes too: builds need `docker buildx --platform linux/amd64`, which it can't do, so easy_sm calls the `docker` CLI with an argv list. Packaging moved from `setup.py`/`setup.cfg`/`base-requirements.txt` to one `pyproject.toml` (hatchling, version read from `easy_sm/__init__.py`, `dev` dependency group).
- **Build order for the rewrite** (chosen 2026-11-03) — on a long-lived `v2` branch, merged when the whole sample workflow works against a real account. (0) clean slate: delete 1.x code, tests and docs machinery, `pyproject.toml`; (1) config: `easy_sm.toml`, lookup order, `--config`, `init`, `env`; (2) runtime module (train entry, stdlib WSGI app under gunicorn, run), tested with plain Python; (3) image: content hash, generated uv Dockerfile, `build`; (4) local loop: `train/run --local`, `endpoints serve/invoke --local`; (5) cloud jobs: `push` via boto3, `train`/`run` with log streaming; (6) endpoints: deploy from job, invoke, ls, describe, delete; (7) `jobs` group and `data upload`; (8) README, CLAUDE.md, 2.0.0 release. Steps 1–4 need no AWS.

# Run command

- **Generic `run` instead of `make`** — the old `make` command (removed in `4eb8302` to simplify the project and focus on Python functionality) is replaced by `run`, which runs any command. Same processing-job path: `SageMakerClient.run()` → `_run_processing(["run", *command])`.
- **Runs from `easy_sm_base/processing/`** — same directory `process` uses (`aa3da62`: processing jobs run inside it so local runs mirror SageMaker), so a `Makefile` or `dbt_project.yml` goes there.
- **`exec "$@"` in `executor.sh`, not `sh -c "$*"`** — arguments reach the tool unchanged. Checked: with `sh -c "$*"`, `python -c 'print("a b")'` is a syntax error and `echo 'x; echo INJECTED'` runs a second command. `exec` also makes the tool PID 1, so its exit code fails the SageMaker job. Shell features need an explicit `-- sh -c "..."`.
- **Trailing arguments after `--`, not a `--command` flag** — a string flag would need re-splitting (`shlex`) and nested quoting, and goes against `docker run` / `uv run` convention. A command already held in one string can use `-- sh -c "$CMD"`.
- **Option parsing stops at the command** (`allow_interspersed_args=False`, `0a4251a`) — without it, `easy_sm run -e ml.m5.large -n job dbt run -e prod` silently submitted instance type `prod`. easy_sm options must come before the command; a command starting with `-` needs `--`.
- **Guard against outdated projects** (`require_run_support`) — an image built from an old `executor.sh` falls through to the model server on `run` and runs until the 24 h processing timeout. The guard checks the project's local `executor.sh` only; an image that wasn't rebuilt and pushed is not detected. Risk accepted for 1.3.0; `--max-runtime` is on the todolist.
- **`executor.sh` still serves on unknown arguments** — making the fallback strict was considered and dropped: it can't help old images (the real risk) and SageMaker hosting relies on the `serve` / no-argument path.
- **`local run` returns the command's exit code** — so it works in CI. Other local commands still exit 0 on failure; left unchanged to avoid breaking existing users.

# Security

- **Env vars passed as separate arguments** (`ce2c366`) — `process_local.sh` used to join `--env` values with commas and expand them unquoted; checked that `MSG=hi --privileged -v /:/host` became real docker flags. Now each `KEY=VALUE` is one argument rebuilt via `"$@"`. `local process --env` refuses to run with the old script (it silently dropped all but the first variable).
- **`~/.aws` stays writable in local containers** — `:ro` would crash SSO users: botocore's `SSOTokenProvider` writes the refreshed token to `~/.aws/sso/cache` without catching errors (checked in botocore `tokens.py`). Proper fix is passing temporary credentials; open.
- **`local deploy` binds to `127.0.0.1`** (`ce2c366`) — previously published on all interfaces. `localhost` URLs unchanged; `stop_local.sh` still matches the container.
- **No secrets in config or job definitions** — credentials were removed from `{app}.json` in favour of boto3's credential chain (`d64173c`); docs warn that `--env` values and `run` arguments are stored in plain text in the SageMaker job.
- **App name validated** (`4eb8302`) — alphanumeric, `-` and `_` only, to block path traversal via `{app_name}.json`; scripts installed `0o755`, not `0o777`.
- **PyPI Trusted Publishing, `pypi` environment limited to `v*` tags** (PR #10, `49b3e69`) — replaces the long-lived `PYPI_TOKEN`. No required reviewer and no tag ruleset: solo repo, chosen 2026-10-13. Verified on 1.3.1: published with no stored token, and PyPI holds attestations for both files. Old token revoked and secret deleted on 2026-10-13, so old-branch workflows (`dev`, `copilot/*`) can't publish.
- **A CI-only patch release to prove publishing** (1.3.1) — released with no package changes so Trusted Publishing was tested while the old token still existed as a fallback, before revoking it.
- **Least-privilege publish jobs** (PR #10) — `build` (read) / `publish` (`id-token: write` only) / `release` (`contents: write`), default `permissions: {}`, so build steps that install packages never get a publishing credential. Archived `actions/create-release` replaced by `gh release create`.
- **Releases only from tags** (PR #10) — `workflow_dispatch` (added in `75db68b` "for testing") removed from publish: it let anyone with write access publish from any branch.
- **Actions pinned to commit SHAs, Dependabot keeps them current** (PR #10) — pins are the versions the floating tags resolved to on 2026-10-13, so no behaviour change; without Dependabot, pins would silently miss security fixes. Dependabot PRs are reviewed, not auto-merged: its first PR (#11) was all major bumps.

# SageMaker SDK

- **SDK pinned to `==2.257.3`** (`ce837b7`) — history: pinned `<3.0.0` "for compatibility" (`9e38f4a`), moved to v3 (`a19683f`), relaxed back to `>=2.243.0` the next day (`ddb0a3b`), then pinned exactly with imports switched from `sagemaker.core.*` to `sagemaker.*`. Reason for the exact pin not recorded beyond "stability".
- **Unique endpoint config per deploy** (`62c900e`, `01dd9fa`) — a fixed `{endpoint}-config` name made redeploys fail with "already existing endpoint configuration"; old configs are cleaned up best-effort, and `delete-endpoint --delete-config` looks up the current config name first.
- **Silence SDK logging before import** (`0a820ed`) — the SDK logs at import time and only honours a log level set beforehand; otherwise the line pollutes pipe-friendly output.

# CI and release

- **Tests on every push, publish only on `v*` tags** (`d73519c`, `4af1623`) — keeps the badge honest; workflow renamed to `publish.yml` to drop the old failing run history. PyPI trusted publisher is bound to that file name.
- **Tag only after CI passes on `main`** (2026-10-13) — a PyPI version can't be re-uploaded. Paid off on 1.3.0: the first `main` run failed (ANSI-sensitive test) and was fixed (`d663439`) before tagging.
- **Minor version for features, patch for fixes** — env vars → 1.1.0, `docker_tag` → 1.2.0, `run` → 1.3.0. Version lives in `setup.py`, `easy_sm/__init__.py`, `mkdocs.yml`.
- **Python `>=3.13`** (`4614cc0`) — 3.14 was tried and dropped because of pydantic problems on the 3.14 release candidate.
- **Pinned `ruff==0.16.2`** (`f7865b9`) — an unpinned ruff in CI picked up new default rules and broke the build without any code change.
- **mypy `warn_return_any = False`** (`49592cf`) — boto3 / SageMaker SDK calls return `Any` (no stubs).

# Testing and docs

- **Mock AWS and Docker in Python tests; run shell scripts for real** — Python tests mock subprocess / boto3 / SDK; `test_local_scripts.py` runs the template scripts with a fake `docker` that records its arguments. Each new script test was checked to fail against the old script.
- **Test against coloured output** — Rich splits flags with ANSI codes when colour is on (GitHub Actions), so tests strip ANSI before matching CLI errors. Reproduce with `FORCE_COLOR=1`.
- **Docs describe only what the code does** (`cfc06a4`, `e25c95d`, `c26de9c`) — unsupported features (hyperparameters, `--tags`) were removed, and `validate_docs.py` + the pre-commit hook guard against drift. Known gap: it compares no flags, because no command page has a `Flag` table header.
- **Three project docs at the repo root, no README** (2026-10-13) — `summary.md`, `decisions.md`, `todolist.txt`. A root `README.md` repo map duplicated CLAUDE.md's structure map and would be mistaken for the user guide (`.github/README.md`), so it was dropped. `summary.md` keeps only state no tool shows, pointing to todolist sections, because version / PRs / CI are one command away and duplicated todos drift.
